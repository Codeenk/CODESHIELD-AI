CodeShield AI – Product Requirements Document
Product: AI-Powered Source Code Vulnerability Scanner & Explainable Auto-Repair Engine Team: Shlok Chavan, Aditya Gaikwad, Sarvesh Malandkar, Yash Bhagwat Institution: Atharva College of Engineering, Dept. of Information Technology (A.Y. 2026-27) Version: 1.0 (improved from the project presentation) Status: Draft for review
1. Overview
CodeShield AI is a web platform and CI/CD service that scans source code for security vulnerabilities, shows exactly which lines and syntax nodes caused each finding, and proposes a validated code fix that a developer can accept with one click.
It combines three things that existing tools offer only separately:
Detection: a fine-tuned CodeBERT classifier, grounded by Tree-sitter ASTs and cross-checked by a rule-based baseline.
Explanation: line-level and AST-node-level attribution with a confidence score and a plain-English rationale mapped to a CWE.
Repair: a fine-tuned Qwen2.5-Coder model that generates a patch, which is then verified (re-scanned and tested) before being shown to the user.
1.1 What changed from the original presentation
The presentation defines a solid idea. This PRD tightens it in the following ways:
Hybrid detection instead of ML-only. Rule-based SAST (Semgrep/Bandit) runs alongside the model. Agreement raises confidence; disagreement is flagged for review. This directly attacks the false-positive problem.
Patches are verified, not just generated. Every proposed fix is re-scanned and, where tests exist, executed before it is presented. Unverified patches are labelled as such.
Explainability is evaluated, not assumed. Attention weights are known to be an imperfect explanation, so the PRD adds a second attribution method (Integrated Gradients/SHAP) and a measurable localisation metric.
Realistic, measurable targets. The deck claims 92%+ accuracy and a 70% MTTR reduction. Those figures come from cited literature and a projected outcome, not from CodeShield itself. This PRD replaces them with targets to be measured on our own held-out data (Section 8).
Scope is staged. MVP covers Python, JavaScript and Java with file and repo scans. C/C++ and multi-file data-flow analysis come in later phases.
Privacy and security of the tool itself (sandboxed execution, no code retention by default) are first-class requirements, since the product ingests proprietary code.
Naming fix. The deck spells the product "CodeSheild" on most slides. The correct name used here is CodeShield AI.
2. Problem Statement
Development teams ship fast through CI/CD and rely heavily on open-source code, which widens the attack surface. Current tooling fails them in three ways:
Noisy. Rule-based SAST tools (SonarQube, Bandit, ESLint security plugins) flag harmless patterns, causing alert fatigue and ignored findings.
Opaque. ML detectors return a score with no explanation of why a block is vulnerable or where the root cause is.
Unactionable. Tools detect but do not fix. General chatbots (ChatGPT, Copilot) can suggest fixes but lack repo context, give no reproducible results and offer no verification.
The result is that developers spend a large share of debugging time manually triaging security alerts (the deck cites over 40%) and known flaw classes keep reaching production.
3. Goals and Non-Goals
3.1 Goals
G1. Detect vulnerabilities in supported languages with precision high enough that developers trust the output.
G2. Explain every finding at line and AST-node level, with CWE mapping and severity.
G3. Generate context-aware patches and verify them before presenting.
G4. Fit into existing workflows: web dashboard, GitHub Action / PR comments, REST API, and later an IDE extension.
G5. Reduce the time from detection to merged fix.
3.2 Non-Goals (v1)
Dynamic testing (DAST), fuzzing or runtime exploitation.
Dependency/SCA scanning (CVE lookup for libraries). Integrate existing tools later rather than rebuild them.
Auto-merging patches without human approval.
Languages beyond Python, JavaScript/TypeScript and Java in the MVP.
Guaranteeing zero false negatives. CodeShield is a decision-support tool, not a certification.

5. User Stories
As a developer, I upload a file or paste a GitHub repo link and get a scan result within a minute for typical files.
As a developer, I see the vulnerable lines highlighted with a heat-map and the responsible AST node called out.
As a developer, I read why this is a vulnerability (CWE, short rationale, example exploit scenario) without leaving the page.
As a developer, I view a before/after diff of a suggested patch, with a badge showing whether it passed verification.
As a developer, I accept a patch and have CodeShield open a pull request.
As a developer, I mark a finding as a false positive or accept-risk, and the system remembers it for that project.
As a security engineer, I filter findings by severity, CWE and status and export a PDF/JSON/SARIF report.
As a team lead, I add CodeShield to GitHub Actions so every PR is scanned and failing thresholds block the merge.

9. Non-Functional Requirements
Security of the tool itself. All cloned or uploaded code is processed in isolated, ephemeral, network-restricted containers. Test execution for patch validation happens only inside the sandbox. Never run uploaded code outside it.
Privacy. Code is not retained after a scan by default (only findings metadata and hashes). Users can opt in to storing code for history. Code is never used for model training without explicit consent.
Data protection. TLS in transit, encryption at rest, secrets scanning so that leaked credentials in code are masked in the UI and reports.
Reliability. Asynchronous job queue with retries; partial results are shown if some files fail.
Scalability. Stateless API workers and a separate GPU inference service that can scale independently; batching of inference requests.
Accessibility and usability. Keyboard-navigable UI, colour-blind-safe severity palette (do not rely on red/green only).
Reproducibility. Model versions, dataset versions and scan configuration are recorded with every result.
Compliance alignment. Findings tagged with CWE and mapped, where possible, to OWASP Top 10 categories.
10. System Architecture
The six-stage flow from the presentation is preserved and extended.
Ingestion service. File upload and GitHub link; language detection; filtering.
Parsing service. Tree-sitter AST generation, function extraction, line maps.
Detection service. Fine-tuned CodeBERT (and rule-based scanner in parallel) with a score calibration layer.
Explainability service. Attention aggregation, optional Integrated Gradients, mapping to AST nodes and lines.
Repair service. Qwen2.5-Coder (LoRA-tuned) generation, candidate ranking, then verification stage (parse, re-scan, optional tests in sandbox).
Presentation layer. Web dashboard, report generator, REST API, GitHub integration.
Suggested stack: React with Monaco Editor (frontend); FastAPI (backend); Celery/Redis or similar job queue; PostgreSQL (metadata and history); object storage for artifacts; PyTorch + Hugging Face Transformers + PEFT for models; Tree-sitter; Docker for sandboxing; GitHub Actions for CI.
11. Machine Learning Specification
11.1 Detection Model
Base model: CodeBERT (RoBERTa-style, pretrained on code and natural language). Evaluate UniXcoder or GraphCodeBERT as alternatives, since they incorporate structure and may suit the AST-centred design.
Datasets: Big-Vul, Devign, CVEfixes, DiverseVul, and the NIST Juliet / SARD suites for CWE-labelled examples. For Python/JS/Java coverage, supplement with CVEfixes (multi-language) and curated samples, because Big-Vul is C/C++ only.
Known dataset risks to manage: label noise, duplicate functions across train and test, class imbalance, and synthetic-vs-real gap (Juliet). Deduplicate, split by project and by time, and use class weighting or focal loss.
Training: fine-tune with a classification head plus a multi-label CWE head; calibrate with temperature scaling.
Long inputs: AST-aware chunking since the model has a 512-token limit.
11.2 Explainability
Aggregate multi-head, multi-layer attention (attention rollout) to token, then to line, then to AST node.
Cross-check with gradient-based attribution; report agreement.
Validate against ground-truth vulnerable lines extracted from fix commits.
11.3 Repair Model
Base: Qwen2.5-Coder (choose a size that fits available GPU, e.g. 1.5B-7B) with LoRA/QLoRA fine-tuning on vulnerability-fix pairs.
Input: vulnerable function, flagged lines, CWE label, brief context (imports, called function signatures).
Output: patched function plus a one-line change summary.
Guardrails: constrained to modify only the flagged function; reject outputs that fail to parse or change public signatures.
11.4 Evaluation Protocol
Hold out a project-disjoint test set; never tune on it.
Compare against: Bandit/Semgrep (rule-based), a plain CodeBERT baseline, and an LLM zero-shot baseline.
Report precision, recall, F1, MCC, AUROC, and per-CWE breakdown.
Include an ablation: with and without AST features, with and without the rule-based ensemble.
12. UX Requirements
Primary flow: Upload or link, then scan progress, then summary, then finding detail with highlighted code, explanation and diff, then accept/reject.
Progressive disclosure: show severity and one-line explanation first; reveal attention maps and technical detail on demand.
Trust cues: always show confidence, verification status of each patch, and which engine (model, rules or both) reported the finding.
Low friction feedback: one-click "false positive" and "helpful / not helpful" controls feed the improvement loop.
Report: executive summary page, per-finding pages with code snippets and recommended fixes, and an appendix with scan configuration and model version.
